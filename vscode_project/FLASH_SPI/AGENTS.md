# Repository Guidelines

## Project Structure & Module Organization
Firmware sources live under `Core/Src`, with headers in `Core/Inc`. Driver code from STM32Cube HAL resides in `Drivers/STM32F1xx_HAL_Driver`, while CMSIS startup and device headers live in `Drivers/CMSIS`. The CubeMX project file `FLASH_SPI.ioc` and linker script `STM32F103XX_FLASH.ld` define the hardware configuration; keep changes to these files in sync with code updates. Build artifacts are generated in `build/<preset>` (Debug or Release); treat the directory as disposable.

## Build, Test, and Development Commands
- `cmake --preset Debug`: configure a Ninja build that targets the STM32F103 with the GCC ARM toolchain.
- `cmake --build --preset Debug`: compile the firmware and emit `build/Debug/FLASH_SPI.elf` plus binaries.
- `cmake --preset Release && cmake --build --preset Release`: produce an optimized image for final validation.
- `arm-none-eabi-size build/Debug/FLASH_SPI.elf`: check section sizes before flashing trimmed devices.

## Coding Style & Naming Conventions
Stick to C11, CubeMX’s two-space indents, and K&R brace placement as seen in `Core/Src/main.c`. HAL initializers and middleware generated by CubeMX must remain inside the `USER CODE BEGIN/END` markers; place custom functions (e.g., `Flash_RunTest`) there to preserve regeneration safety. Name public symbols with module prefixes (`Flash_`, `MX_`) and use uppercase snake case for macros and constants.

## Testing Guidelines
At minimum, exercise the on-board flash test sequence (`Flash_RunTest`) after each functional change. Extend tests by logging SPI transactions over `flash_tx_buffer`/`flash_rx_buffer` for regression comparison. When adding automated checks, keep them board-agnostic so they can run under host emulation before hardware deployment.

## Commit & Pull Request Guidelines
Write imperative, scope-first commit messages inspired by `git log` (`init FLASH_SPI driver`). Each commit should cover a single concern and describe hardware implications when relevant (`gpio: update chip-select pin mapping`). Pull requests need a concise summary, any linked tracker item, steps for verification (build preset + bench procedure), and photos or logic traces when hardware behavior changes.

## Hardware & Debug Tips
Document probe and jumper selections alongside firmware changes. When debugging, keep the corresponding `gdb` or serial monitor command in the PR so others can reproduce timing-sensitive issues.
